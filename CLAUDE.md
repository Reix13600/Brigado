# Brigado — Project Context for Claude Code

Staff hours, roster, and payroll SaaS for French restaurants (HCR sector). Built with Firebase (Hosting, Firestore, Auth, Cloud Functions), React + TypeScript + Vite. Stripe for billing, Resend for transactional email.

## Stack & structure

* `src/` — React app. `App.tsx` handles routing (slug-based: `/{restaurantSlug}` = the app, `/` = public Landing page, `/mentions-legales` `/cgv` `/confidentialite` `/contact` `/features` = static marketing pages).
* `src/components/ManagerDashboard.tsx` and `StaffDashboard.tsx` — the two main views. ManagerDashboard is very large (~5000 lines); most features live here.
* `functions/` — separate Node project (own `package.json`/`tsconfig.json`), Cloud Functions v2. Deploy separately from hosting: `firebase deploy --only functions` vs `firebase deploy --only hosting`.
* Firestore structure: `restaurants/{slug}` (config, staff array, revenueByWeek, ownerContact, managerEmails) with subcollections `entries`, `advances`, `scheduledShifts`, `activeClockIns`, `announcements`, `messages`, `timeOffRequests`, `swapRequests`. Separate `managers/{uid} -> {restaurantId, email}` lookup collection (supports multiple managers per restaurant, all equal access).
* Production domain: `brigado.solutions` (Firebase Hosting custom domain). Firebase project: `brigado-a33b1`.

## Business context

* Pricing: EUR 39/month or EUR 390/year, 7-day free trial, card required upfront. Stripe Payment Links (not custom Checkout code) with `trial_period_days` set per-link.
* Registration flow: RegisterPage collects restaurant name/slug/email/contact name/phone (required)/city (required, added Aug 2026)/postcode (optional) -> Stripe Payment Link (all fields ride in `client_reference_id`, pipe-delimited, along with the page's FR/EN toggle state) -> webhook (`stripeWebhook` in functions) provisions the restaurant, manager account, and sends a password-setup email via Resend. Provisioning stores `signupEmail` (the durable "main registered contact" — survives later manager add/remove), `preferredLang`, and `ownerContact: { contactName, phone, postcode, city }` on the tenant doc.
* Target market: French restaurants/small hotels. French is the default language everywhere (`lang` state defaults to `"fr"`); English is a toggle, not the primary language.
* Competitor context: Combo/Snapshift charges per-employee (~EUR 5-7/employee/mo); Brigado's flat fee is a deliberate differentiator for restaurants with bigger teams.

## Key architectural decisions (don't relitigate without reason)

* Trust model: staff use anonymous Firebase Auth (no real accounts, identity enforced by in-app PIN only) — this was a deliberate simplicity choice. Managers use real email/password or Google auth.
* No hard-deletes of staff data by default. Archiving a staff member (`active: false`) hides them from active rosters but never touches their historical entries/payroll — this is intentional, for French payroll record retention (~5 years). Permanent deletion is only exposed in the UI once 5+ years have passed since their last logged activity (see the Former Staff popup in ManagerDashboard).
* Compliance engine (`src/utils/compliance.ts`) cites real Code du travail articles + the HCR collective agreement. Every rule is individually toggleable (not all-or-nothing), defaults to only the 4 near-universal rules being on. There's an explicit "what this does NOT track" disclaimer in the UI — never remove that; overstating legal coverage is a real liability, not just a copy nitpick.
* Print-safe portals: any printable document (QR poster, Timesheet, Bookkeeper export) renders via `createPortal` to `document.body` with class `print-portal-root`. The print CSS in `src/index.css` hides everything except that portal using `body:has(.print-portal-root) > *:not(.print-portal-root) { display: none }`. Do NOT put `print:hidden` on the portal's own root element — that was a real bug once (hides the print area along with everything else). Do NOT remove the `:has()` guard — without it, printing anything else in the app (Roster Planner, Entries) goes blank.
* Messages auto-delete after 30 days (`cleanupOldMessages` scheduled function) — private chat only, NOT announcements, NOT entries/payroll (those are kept indefinitely, no retention automation built yet beyond the 5-year staff-deletion gate above).
* Bilingual pattern: most newer components use inline `lang === "fr" ? "..." : "..."` rather than the `translations.ts` dictionary (which covers older/core UI). Both patterns coexist; match whichever pattern the file you're editing already uses.

## Trial expiry, blocking & 30-day purge (do not "fix" or revert)

* **DEPLOYED 2026-08-12** to `brigado-a33b1` (functions → hosting → firestore:rules). Live as of that date: the trial-expiry state machine, `TrialExpiredScreen`, the `createBillingPortalSession` callable, `purgeExpiredTrials`, and — new that day — **Firestore rules enforcement** of the block. Verified in production after deploy: 21/21 client-SDK checks (blocked tenant's 8 subcollections denied read + write to an anonymous session; `la-vague` wholly unaffected), plus 50/50 emulator rules tests. Brevo shipped **inert** on this deploy — see the Brevo section.
* **States**: `restaurants/{slug}.subscriptionStatus` is the single source of truth for access blocking — `"active"` or `"trial_expired"`. Written ONLY by the Stripe webhook functions (never recomputed from dates client-side). `"trial_expired"` means the trial ended without ever converting: subscription canceled/deleted, terminal status (`canceled`/`unpaid`/`incomplete_expired`), or first payment failed for a customer who has NEVER had a paid invoice. A failed *renewal* for a previously-paying customer does NOT block (Stripe dunning handles it; a terminal status later will). `trialExpiredAt` (ISO) starts the 30-day deletion clock and is deliberately NOT reset by repeated expiry events. `suspended` is a legacy mirror kept in sync so stale client builds still block.
* **Blocking enforcement — TWO layers, both required**:
  1. *UI (App.tsx)*: gates the entire `/{slug}` app before either dashboard mounts — staff PIN pad and manager login are both unreachable when `subscriptionStatus === "trial_expired"` (renders `TrialExpiredScreen.tsx` instead). A live `onSnapshot` on the tenant doc means already-open sessions get blocked (or unblocked) in real time.
  2. *Firestore rules (added 2026-08-12)*: `tenantBlocked(restaurantId)` in `firestore.rules` reads `subscriptionStatus` off the parent tenant doc and is ANDed into every subcollection read and write, plus writes to the tenant doc. Until this existed, blocking was UI-only — anyone with the slug and an anonymous session could read/write a blocked tenant's data straight through the SDK. Do not drop this layer; the UI gate alone is not a security boundary.
* **Three things in that rules design are load-bearing — do not "tidy" them away**:
  * `.data.get('subscriptionStatus', '')` defaults a **missing** field to not-blocked. Tenants provisioned before the field existed (incl. `la-vague`, which has no `subscriptionStatus` at all) must keep working. Only the literal string `"trial_expired"` ever blocks.
  * The tenant doc itself stays **readable** while blocked — it is the doc App.tsx fetches and live-watches to discover it is blocked. Denying it replaces the explanatory block screen with a generic connection error.
  * `managers/{uid}` is **deliberately NOT gated** on subscription status: `isAuthorizedManager()` reads it during reactivation, so blocking it would break the only path an expired tenant has to pay and return. It leaks nothing (own-uid read only, `write: if false`).
* **`fetchAppData` skips subcollection reads when blocked** (`src/utils/api.ts`). This is not an optimization — it is required. `fetchAppData` `Promise.all`s all 8 subcollections, and App.tsx checks `error` *before* `trial_expired`, so a rules denial would surface as the generic "Failed to load" screen and hide the block screen (and its reactivation sign-in) behind a dead end. Keyed off the same field as the rules so the two cannot disagree.
* **Reactivation**: `TrialExpiredScreen` has its own manager sign-in (email/password + Google) which then calls the `createBillingPortalSession` callable → Stripe billing portal. That callable REQUIRES a verified manager of the restaurant — never make it unauthenticated; the portal URL exposes billing data. A successful payment (`invoice.paid` with `amount_paid > 0`), a subscription returning to `active`, or a fresh checkout with the same slug all clear the block via the webhook.
* **30-day purge**: `purgeExpiredTrials` (daily, 04:30 Paris) permanently deletes tenants with `subscriptionStatus === "trial_expired"` for 30+ days — audit record to top-level `deletionAudit` collection first (PII-light: slug, counts, timestamps), then manager lookup docs + their Auth accounts, then `recursiveDelete` of the restaurant doc and all subcollections. No Firebase Storage cleanup because the app stores nothing in Storage. **Reminder/warning emails during the 30 days are NOT sent at all right now.** They were removed from code (the old day-23 Resend final notice, deleted Aug 2026) on the assumption that a Brevo "Trial Expired" automation would replace them — **that automation was never built, and the list it would trigger from does not exist** (see the Brevo section). So the 30 days currently run silently to deletion; the block screen is the only notice, and only if the customer tries to log in.
* **Safety rail**: before ANY notice or deletion, the job re-checks live Stripe — if the customer has an `active`/`trialing`/`past_due` subscription, the flag is treated as a missed-webhook error, access is restored, and nothing is deleted. A Stripe API error skips that tenant until the next run. All transitions log loudly (reason + event id stored in `subscriptionStatusReason`) for manual investigation.
* **GDPR reasoning**: this purge applies ONLY to tenants that never became paying customers — there is no contract and no payroll-retention duty on Brigado's side, so holding their staff PII indefinitely would itself be the exposure. 30 days' retention with emailed warnings before erasure would be a standard, defensible policy — **but note the warnings are not currently being sent** (see the purge bullet above), so as of 2026-08-12 the policy as *implemented* is 30 days' silent retention then deletion. That is a materially weaker position than the one this reasoning was written to describe, and it is the strongest practical argument for finishing the Brevo sequence. This is entirely separate from (and must not be merged with) the 5-year staff-record retention on active accounts. Known gap, deliberate: no proactive `trial_will_end` warning email (the webhook only stamps `trialWillEndNotedAt`).

## Working style established with this project

* Always run `npx tsc --noEmit` and a full `npm run build` (both root app and `functions/` separately) before considering a change done.
* Deploys: `firebase deploy --only hosting` for app changes, `firebase deploy --only functions` for Cloud Functions changes (both if both changed). `firebase use brigado-a33b1` to confirm the right project before deploying (there was a past incident of deploying to the wrong Firebase project).
* The user (Reix) runs a real restaurant (La Vague, slug `la-vague`) as the pilot customer — treat that restaurant's data/settings as real production data, not a test fixture.
* **Documentation hygiene — verify before writing "done" in this file.** Only record something as done, existing, or working after confirming it **from the authoritative source**: for an external service (Brevo, Stripe, Resend, Firebase console) that means its own dashboard or API, not the code. Code compiling, a function deploying, or a call returning 200 proves none of these things — a guarded call that logs and skips also "succeeds". This rule exists because the 2026-08-12 session found **three separate false "done" claims** in this file that ordinary code review had not caught: a Brevo list that was never created, a setup script that never existed under the name given, and a set of contact attributes that were documented as "all exist" when 7 of 9 did not. Each looked correct in the source. When you cannot verify something, write down what you could not verify and why — an explicit unknown is useful, a confident wrong claim is worse than silence.
* Prefer testing security rules against the **Firestore emulator** (`firebase emulators:exec --only firestore`) rather than reasoning about them. Rules changes are hard to reason about and easy to get subtly wrong — the trial-expiry rules landed with 50 emulator assertions covering active / legacy-missing-field / blocked tenants plus cross-tenant and unauthenticated access, then 21 more against production after deploy. Java is required for the emulator and is installed on this machine; port 8080 is occupied, so pass a config with a free port.
